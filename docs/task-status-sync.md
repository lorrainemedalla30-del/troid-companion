# Task status updates → Supabase

When an operator taps **UPDATE STATUS** (Explore → Task Status), the Troid
Companion app sends the update to the TROID system's backend
(`POST /api/companion/task-status/`, signed in as the operator). The backend
inserts one row into a Supabase table, filling in `operator_email` from the
operator's account, so an update can't be sent in someone else's name. Your
system reads that table, or is notified the moment a row arrives.

The app never talks to Supabase itself and holds no Supabase key.

## 1. Create the table

Run this once in Supabase → **SQL Editor**:

```sql
create table public.task_status_updates (
  id             uuid primary key,             -- generated by the app; makes retries safe
  status         text not null
                 check (status in ('completed', 'to_be_continued', 'in_progress')),
  notes          text,                         -- optional operator notes
  operator_email text,                         -- email the operator logged in with
  created_at     timestamptz not null,         -- when the operator tapped UPDATE STATUS (phone clock)
  received_at    timestamptz not null default now()  -- when Supabase stored it
);

-- Row Level Security with no policies: the public (anon) key can do nothing.
-- Only the TROID backend's secret key, which bypasses RLS, can read or insert.
alter table public.task_status_updates enable row level security;
```

**Upgrading from the earlier setup**, where the app inserted with the public key:
remove that policy, or anyone holding the public key could still insert fake rows.

```sql
drop policy if exists "Troid Companion can insert status updates" on public.task_status_updates;
```

The TROID backend reads and writes the table with a **secret key**
(`sb_secret_...`, or the legacy service role key), set on Render as
`SUPABASE_URL` and `SUPABASE_SECRET_KEY`. Use it on servers only, never in an
app; it bypasses RLS.

## 2. Get the updates into your system

### Option A (recommended): read the table

Your system reads new rows from Supabase. Nothing extra to set up in Supabase,
and nothing is missed if your system is down for a while: the updates wait in
the table.

You need, from Supabase → Project Settings → API Keys:

- the project URL: `https://terkfuubjjbelwcqpish.supabase.co`
- a **secret key** (`sb_secret_...`). Create one just for your system so it can
  be revoked on its own. Keep it on your server only.

**Over plain HTTPS** (any language):

```bash
curl "https://terkfuubjjbelwcqpish.supabase.co/rest/v1/task_status_updates?select=*&order=received_at.asc&received_at=gt.2026-10-11T00:00:00Z" \
  -H "apikey: sb_secret_..."
```

Returns a JSON array of rows newer than the given time.

**With JavaScript / Node** (`npm install @supabase/supabase-js`):

```js
import { createClient } from '@supabase/supabase-js';

const supabase = createClient('https://terkfuubjjbelwcqpish.supabase.co', process.env.SUPABASE_SECRET_KEY);

const { data, error } = await supabase
  .from('task_status_updates')
  .select('*')
  .gt('received_at', lastCheckedAt)   // ISO time of your previous check
  .order('received_at', { ascending: true });
```

**Checking regularly (polling):** run the query on a schedule (e.g. every
minute) and remember the newest `received_at` you have processed. Rows that
arrive at almost the same moment can appear slightly out of order, so query
from a minute before that time and skip any `id` you already have.

**Instantly instead of polling (Realtime):** run once in the SQL Editor:

```sql
alter publication supabase_realtime add table public.task_status_updates;
```

then subscribe from your server:

```js
supabase
  .channel('task-status')
  .on('postgres_changes', { event: 'INSERT', schema: 'public', table: 'task_status_updates' },
      payload => saveToYourSystem(payload.new))
  .subscribe();
```

Realtime only delivers rows while your system is connected, so also run the
polling query on startup to catch anything missed.

**Times** (`created_at`, `received_at`) are stored in UTC. Convert to Philippine
time (UTC+8) when displaying them.

### Option B: email / SMS alerts

A Supabase Edge Function sends a message to staff for each new update. Not set
up yet; ask the app team.

### Option C: webhook (push to your system's URL)

Use this only if your system must receive each update the instant it arrives
and cannot read from Supabase. Supabase → Integrations (or Database) →
**Database Webhooks** → *Create a new hook*: table `task_status_updates`, event
**Insert**, method **POST**, your endpoint's URL, and a header such as
`Authorization: Bearer <shared secret>` that your endpoint checks. Supabase
POSTs each new row as JSON:

```json
{ "type": "INSERT", "table": "task_status_updates", "schema": "public",
  "record": { "id": "…", "status": "completed", "notes": "…", "operator_email": "…",
              "created_at": "…", "received_at": "…" },
  "old_record": null }
```

Your endpoint should reply with a 2xx status quickly.

## 3. Configure the app

Copy `.env.example` to `.env.local` and set the TROID backend's address:

```
EXPO_PUBLIC_TROID_API_BASE=https://troid-sys-22ps.onrender.com/api
```

Restart `npx expo start` after changing it; it is baked in when the app is bundled.
The Supabase settings live only on the backend (`SUPABASE_URL`,
`SUPABASE_SECRET_KEY` on Render).

## How delivery works

- Every update is **saved on the phone first**, then sent. If the phone is
  offline (for example, out of range of the bot's hotspot), it stays queued
  and is sent automatically when the phone is back online, when the app next
  starts, or every 30 seconds while anything is waiting. Updates are sent in
  the order they were made.
- Each queued update remembers which operator made it and is only sent while
  that operator is signed in. If an operator logs out with unsent updates, they
  wait on the phone until that operator logs in again.
- Each update has a unique `id` (the primary key). If a retry repeats an update
  that already arrived, Postgres rejects it as a duplicate and the backend counts
  it as delivered, so a dropped connection never creates a second row.
- If the backend rejects an update for good (for example, notes over 2000
  characters), the operator sees the reason and it is not retried.
- If Supabase is down or misconfigured on the backend, or the operator's session
  has ended, nothing is lost: updates stay queued and are sent once that is fixed
  or the operator signs in again.
